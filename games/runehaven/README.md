# 룬빛 상회

대장간·잡화점·연금 공방·여관을 운영하는 모바일 웹 판타지 게임이다. 무기·물약과 주방 음식을 머리 위로 나르고 판매해 마법을 강화한다. 여관 손님은 배식대에서 음식을 받아 식탁에 앉아 먹으며, 사용한 식탁은 주인공이나 정리 담당 조수가 정리해 다시 쓴다. 조수에게 무기·물약·음식 운반과 식탁 정리 중 하나를 맡길 수 있다. 구매 손님은 전사에서 궁수·마법사로 늘어나며, 습격이 오면 돌아와 상회를 방어한다. 이동을 마지막까지 강화하면 짧은 순간이동을 사용한다.

Burger Please!의 실제 본체 APK 31.6.0과 플레이 영상을 대조해 생산·운반·판매·식탁 운영을 참고했다. 식탁 개방 비용·2좌석·조수 상한과 일반 주문 후보의 산술을 확인했고, 빈자리·청소 대기·여러 개 주문·마주 앉은 손님·식탁별 대금은 영상에서도 관찰했다. 근거와 미확정 사항은 [APK_SERVICE_REVIEW.md](data/APK_SERVICE_REVIEW.md)에 기록했다. 사용자의 원본 그래픽 재사용 요청에 따라 본체 APK에서 추출한 캐릭터·카운터·그릴·식탁·의자·버거·컵·돈 등 11종 메시를 사용하고 색을 바꾼다. 원본 면·정점 연결을 유지하되 웹 크기·피벗·관절 연결과 동작은 변환한다. 원작 코드·이미지·음원·UI 전체를 이식한 것은 아니다. [아트 기준](assets/ART.md)을 따른다.

- 로컬 경로: `/games/runehaven/`
- 공개 배포 시 경로: `https://lunarelin.github.io/games/runehaven/`
- 홈 복귀: `../../`

저장소 루트를 제공하는 기존 정적 서버를 우선 재사용한다. 새 서버가 필요하면 저장소 루트에서 다음과 같이 실행한다. Windows의 `.mjs` MIME 연결과 무관하게 모듈을 올바른 타입으로 제공한다.

```powershell
node games/runehaven/tests/serve.mjs
```

이 경우 `http://127.0.0.1:8765/games/runehaven/`로 접속한다. 디렉터리의 `index.html`과 `.mjs`의 JavaScript MIME 타입을 지원하는 서버가 필요하다. 게임 실행을 위한 루트 패키지 설치 과정은 없다. Three.js r170(0.170.0)은 `vendor/`에 로컬로 제공하고 화면·입력은 일반 ES 모듈로 연결한다. 현재 인물·시설·가구는 선택 원본 메시를 약 244KB의 로컬 데이터 모듈로 제공하며 GLB·OBJ 파서·Unity 런타임의 초기 다운로드·사전 로드를 하지 않는다. 이전 GLB와 로더는 보관·자산 회귀 검증용으로 남겨 두었다. 라이브러리·이미지·글꼴의 출처와 라이선스는 해당 로컬 라이선스 파일 및 `assets/SOURCES.md`에 기록한다.

## 조작과 핵심 규칙

휴대폰에서는 바닥·작업장 표식을 누르거나 화면 조이스틱으로 이동한다. 흰 작업 원(반경 0.48) 안에서 0.4초 정지하면 0.22초 간격으로 물건을 하나씩 싣거나 내린다. 이동 중에는 상하차하지 않으며 운반물은 캐릭터 머리 위 스택으로 표시한다. 판매·식사 매출은 소지금에 바로 들어가지 않고 해당 가게의 현금 더미에 쌓인다. 초록 수금 원(반경 0.5) 안에 멈추면 직접 회수한다. 움직이며 지나가는 동안에는 회수하지 않는다. 방어 승리 보상은 소지금에 바로 지급한다. 이 거리·시간은 이 웹게임에 맞춰 별도로 정한 규칙이다.

운반량 게이지는 현재 짐과 강화된 최대 용량을 표시한다. 작업 중에는 별도 진행 게이지로 쌓기·내려놓기·자리 정리를 보여 주며, 맨 앞 손님의 주문 말풍선은 품목·받은 수/전체 수·전달 진행 또는 대기 이유를 표시한다. 머리 위 스택과 고객 손 앞의 물건 묶음은 받은 실제 수량을 따른다. 물건은 출발 스택의 해당 층에서 목적지의 다음 층으로 포물선을 그리며 이동하고, 비행 중인 물건이 도착 스택에 중복 나타나지 않게 한다. 음식 층 간격 0.16·작은 물약 0.31과 비행 시간 0.18초는 웹 표현값이다. 원작의 모든 게이지 용도나 정확한 상하차 시간을 복원한 값은 아니다.

각 시설의 흰 작업 원은 몸체 밖에 있으며 `getStationApproach()`와 실제 작업 판정·바닥 링·이동 버튼이 같은 `getWorkZone()` 좌표를 사용한다. 무기·물약 진열대는 뒤쪽, 생산 시설은 앞쪽에서 작업해 손님 앞줄과 분리한다. 몸체와 작업 원을 따로 추정하지 않는다. 각 원의 반경과 접근 거리는 웹게임 값이며 실제 원본 메시 외곽·의자·다른 행동 원과 겹치지 않는지 10개 지역에서 검사한다.

작업장·수금·식탁 표식과 바닥 탭은 빈 바닥에서 목표까지 직선으로 이동하고, 고정 시설의 작은 몸체가 막는 구간만 돌아간다. 조수와 손님도 같은 고정 몸체를 피하며, 조이스틱은 몸체 경계에서 막히거나 미끄러진다. 손님은 공통 입구 줄에서 순서대로 들어와 분기점을 지난 뒤 각 진열대의 짧은 줄로 향한다. 영업 중 인물끼리 겹치는 것은 허용하고 손님 줄을 장애물로 삼거나 조수 자리를 분산·밀어내는 계산은 사용하지 않는다. 넓은 작업 감지 영역과 작은 시설 몸체를 나눈 APK 구조를 참고했으며 웹의 치수·경로 계산은 새 구현이다. 전투의 기존 같은 편 분리 규칙은 유지한다.

일반 상품·음식 주문은 식탁 0~1개에서 1개, 2~3개에서 1~2개, 4개에서 2~3개다. 무기·물약은 카운터 단계의 2 / 1.5 / 0.9초로 첫 물건 전달을 준비하고 같은 주문의 나머지는 0.22초마다 한 개씩 준다. 주문을 모두 전달한 뒤 수량×첫 전달 시 확정한 단가로 매출을 적립하고 판매 횟수·단골 등록은 주문당 한 번만 증가한다. 일부 전달분은 완료 전까지 매출·단골을 만들지 않는다. 원작의 일반 주문 후보 범위를 판타지 품목에 적용했으며 원작 튜토리얼·VIP·전화 주문의 모든 분기와 품목 배분을 그대로 옮긴 것은 아니다.

판매 16회 뒤 5골드로 여관을 개방하면 주방·배식대와 첫 식탁을 사용할 수 있다. 다음 식탁은 50→150→200골드로 하나씩 구매해 최대 4개까지 늘린다. 시설 메뉴나 다음 식탁의 파란 바닥 원을 선택해 이동하고, 그 원에 서서 개방한다. 이 비용은 본체 APK의 Stage1 TableArea 첫 레벨 값이다. 음식은 주방에 3초마다 1그릇씩 자동 조리해 최대 8그릇까지 쌓인다. 주방의 초기 음식은 4그릇이고 배식대는 비어 있으며, 배식대에도 최대 8그릇까지 놓을 수 있다. 주인공이 주방 앞에서 멈춰 음식을 머리 위에 싣고, 배식대까지 직접 운반해 멈추면 하나씩 내린다. 무기·물약·음식은 같은 운반량을 나눠 쓰며 0.4초 정지 대기·0.22초 상하차 간격도 같다. 음식이 주방에서 배식대로 자동 전송되지는 않는다.

식탁마다 마주 보는 2좌석이 있으며 각 자리의 예약·착석·식사·정리를 독립적으로 관리한다. 구매 손님의 60%가 최대 4명까지 배식 줄에 들어간다. 맨 앞 손님은 배식대 음식과 깨끗한 빈자리가 있으면 자리를 예약하고 첫 그릇을 받으며, 나머지를 0.22초마다 받아 주문을 모두 채운 뒤 식탁으로 이동한다. 식사 시간은 수량과 별개로 여관 단계에 따라 5 / 4.7 / 3.7초다. 식사가 끝나면 수량만큼의 대금을 해당 식탁 옆에 남기고 단골은 회복·충성도 1을 얻는다. 식탁마다 현금이 독립적으로 쌓이며, 직접 접근한 더미만 수거한다. 사용한 자리는 식기가 남은 정리 대상으로 바뀌고, 주인공이 가까이 가서 1.2초 정지하거나 정리 담당 조수가 작업하면 다시 쓴다. 같은 식탁의 다른 자리는 계속 식사하거나 새 손님을 받을 수 있다. 주인공이 이동하면 자신의 정리 진행이 초기화된다. 깨끗한 빈자리가 모두 없으면 새 배식을 시작하지 않으며, 부분 주문 중 음식이 떨어지면 받은 그릇을 유지하고 보충을 기다린다.

고용 화면에서는 각 조수의 담당을 무기 운반·물약 운반·음식 운반·식탁 정리 중 하나로 지정한다. 음식 담당은 주방과 배식대를 오가며 실제 음식을 싣고 내리고, 정리 담당은 사용한 식탁에 가서 1.2초 동안 정리한다. 담당을 바꿀 때 이미 든 짐은 원래 진열대나 배식대에 먼저 내려놓고 새 일을 시작한다. 다만 정리 담당의 기존 납품처가 가득 차면 식탁을 먼저 정리하고, 빈자리가 생기면 든 짐을 내려놓는다. 음식이 가득한 배식대와 더러운 식탁 때문에 운영이 함께 멈추는 것을 막는다. 직접 지정한 담당은 연금 공방을 새로 열어도 유지한다. 고용 상한은 본체 APK의 WorkerData_Stage1.maxEmploy에 맞춰 5명이며, 기존 비용·공유 속도/운반 훈련은 유지한다.

식사 시간·기본 매출 24·단계별 보너스는 여관에 적용한 기존 시설 수치를 재사용한다. 개별 식탁 개방·2좌석·식탁별 현금·일반 주문 후보·최대 조수 5명은 APK와 영상 근거를 반영했다. 음식 운반과 조수 직무, 정리 시간, 회복·충성도 연결은 웹게임의 해석이다. 원작의 전체 주문 분배와 정확한 조리·상하차·정리 상수는 미확정이다.

정리할 자리가 여러 개면 가장 가까운 한 자리에 `정리` 표식을 표시한다. 다른 자리도 바닥을 직접 눌러 이동할 수 있으며 가까이 멈추면 같은 방식으로 정리한다. 식사 중인 손님과 좌석별 음식, 사용 후 빈 그릇을 장면 안에서 구분한다.

플레이어·시설·조수 강화와 고용·건설·식탁 개방은 해당 파란 바닥 원(반경 0.55) 안에 정지해야 지불할 수 있다. 화면 메뉴는 원 밖에서 즉시 구매하지 않고 해당 원으로 안내한다. 조이스틱으로 직접 들어가 0.25초 멈춰도 메뉴가 열리며, 닫은 메뉴는 원 밖 0.12 여유까지 벗어날 때까지 다시 열리지 않는다. 조수 업무 지정은 무료다. 순간이동·일시 정지·재시작은 기존 버튼을 사용한다. PC에서는 화면 조작과 키보드 이동을 함께 제공한다. 자세한 화면별 안내는 게임 안 도움말을 기준으로 한다.

오른쪽 위 **메뉴 → 진행 초기화**로 새 상회를 시작한다. 시작 화면에서도 바로 초기화할 수 있으며, 확인 전 취소·닫기·Escape는 원래 화면으로 돌아간다. 확인하면 이 게임의 골드·강화·시설·조수·단골을 새 상태로 덮어쓴다. 다른 게임의 저장은 변경하지 않는다.

영업 카메라는 일정한 각도를 유지하며 플레이어를 따라간다. 상회 가장자리에서는 이동을 제한하고, 높은 짐이 상단에 닿으면 필요한 만큼 시야를 넓힌다. 순간이동·지역 이전·재시작·화면 크기 변경에는 구도를 즉시 맞춘다. 전투 카메라는 가까운 접점·최근 공격 부근의 밀집 교전을 고르고 실제 공격자의 위치와 목표를 함께 확인한다. 원거리 공격자와 피격 대상, 머리·무기 동작의 여백을 고려해 같은 교전이 화면 끝에서 잘리지 않게 추적한다. 건물·입구·문 앞 주인공·멀리 대기하는 증원을 모두 담으려고 축소하지 않는다. 결과에서는 마지막 교전 구도를 유지하고 영업으로 돌아오면 기존 플레이어 추적 구도로 복귀한다. 모바일 작업장 표식은 52px 그림 버튼이며, 화면 밖 작업장은 테두리가 점선인 표식으로 안내한다.

전투 배율은 `min(60, 플레이 영역 폭 / 6.4, 플레이 영역 높이 / 6.5)` CSS px/world unit을 기준으로 고정한다. 인물이 흩어지거나 증원 수가 바뀌어도 확대율이 반복해서 변하지 않는다. 전투 전용 추적은 0.12 월드 단위 안의 작은 목표 흔들림을 무시하고 이동을 완화한다. 선택한 공격자의 몸·무기와 표적에 좌우 40·위 48·아래 52 CSS px의 목표 여백을 잡고, 실제 카메라 위치에는 최소 좌우 24·위 38·아래 42px를 적용한다. 목표 여백이 긴 공격 쌍을 담기에 좁으면 해당 축만 최소 여백으로 맞춘다. 완화된 위치가 최소 여백을 벗어나면 필요한 만큼 바로 보정해 교대 첫 화면에도 여유를 확보한다. 유효한 원거리 교전은 공격 동작 뒤 0.18초 더 유지해 잦은 교대를 줄이되 죽거나 멀어진 교전은 즉시 해제한다. 실제 화면 이동이 한 프레임에 24 CSS px를 넘으면 직전 안전 구도에서 새 안전 구도로 0.26초 교차 페이드한다. 두 화면의 인물 크기는 같고, 축소하거나 빈 중간 지점을 길게 훑지 않는다. 첫 출전·화면 크기 변경은 이전 영상을 버리고 구도를 맞추며, 결과에서는 마지막 위치를 유지한다. 이 수치와 추적 정책은 새 판타지 웹게임 설계다.

영업 시 가로 시야는 기본 9.4 월드 단위다. 일반 고객은 주인공의 동일 몸 모델 대비 72%, 조수 92%, 수호대 90% 크기로 표시한다. 적은 보병 95%·돌격/원거리 90%·정예 122% 크기와 전투 무기로 구분한다. 실내는 24×24로 넓혀 양옆 생산·진열 시설과 뒤쪽 여관·주방·식탁을 떨어뜨렸다. 실제 모델 크기·높이·회전을 반영한 주요 시설 묶음 11개는 10개 지역 모두 바깥 윤곽 사이 최소 1.3 월드 단위 간격을 둔다. 이 비율·치수는 영상을 참고해 새로 정한 웹게임 값이다.

초반에는 실제 미결제 손님 12명까지 유입하고, 판매/시설 개방에 따라 최대 대기 24명·전체 30명까지 늘어난다. 상점 밖에는 최대 24자리의 공통 입구 줄이 있고 맨 앞 손님부터 0.55초 간격으로 입장한다. 입구 안의 분기점을 지난 뒤 구매 품목에 맞는 무기·물약 진열대 앞 6자리 줄로 향한다. 줄이 찬 품목의 손님이 맨 앞이면 자리가 날 때까지 입구에서 기다린다. 바닥의 갈림길과 대기 표식으로 이 흐름을 보여 주며, 줄은 인물을 막는 물리 장벽이 아니다.

첫 6명을 채울 때 최대 0.65초 간격으로 오며 이후 도착 간격은 `counter.seconds / (공방 개방 ? 2 : 1) × 0.75`를 0.3~1초로 제한한다. 빨라진 시설에도 줄이 이어지도록 수요를 늘린 것이며 기존 결제 시간·가격·생산 재고는 그대로 적용한다. 무기/물약 손님은 실제 물건을 사고 매출을 바닥에 남기며 구매 단골만 방어에 합류한다.

상품 줄이 가득 찼을 때 이미 뽑힌 손님의 직업을 다른 직업으로 다시 뽑지 않는다. 입장 가능한 자리가 생길 때까지 그 선택을 유지해 무기 줄 포화가 마법사 위주 유입으로 이어지지 않게 한다. 대기 목표는 최대 24명이지만 직업 선택과 상품별 16자리 제한에 따라 무재고 상태의 실제 대기는 20~24명일 수 있다.

주인공은 보라 모자·앞치마, 일반 고객은 파랑 단색 몸, 조수는 노랑, 수호대는 초록, 적은 진한 자주색으로 구분한다. 원본 손님은 얼굴 장식 없는 196 triangles, 주인공·조수 등은 원본 몸과 앞치마를 합친 1,840 triangles·8 bones·1 draw다. 이전 요정 얼굴·하트·머리방울은 제거했다. 원본 T 자세의 팔과 가중치를 웹 관절에 연결하며 실제 원작 애니메이션 클립·셰이더를 복제한 것은 아니다. 기존 몸 높이 1.3과 역할별 배율·전투 확대율을 유지한다.

상품은 원본 버거·컵, 음식은 다른 색 버거, 식사 후 남은 것은 원본 빈 포장지다. 바닥 대금과 수금 이동도 원본 지폐 형상이다. 원본 시설에 맞춰 선반을 배치하고, 선반 위 실제 지지면과 재고·비행 출발/도착점을 함께 검사한다. 새 외부 이미지 파일은 추가하지 않았으며 선택 메시·재질·인스턴스 버퍼를 공유한다.

바닥은 촘촘한 타일 대신 큰 단색 판과 낮은 대비의 색면 최대 2개, 지역 장식은 대표 실루엣 2개로 줄였다. 시설과 식탁·의자는 선택 원본 메시로 표현하고 출력 선반은 원본 식탁을 조합한다. 금테·기둥 장식·룬·야외 디딤돌·계속 떠오르는 화덕 불꽃과 추가 포인트 조명을 제거했다. 머리 위 물건·바닥 대금·입구 줄과 분기, 음식·사용한 식탁 상태는 유지한다.

모바일에서는 렌더 해상도 배율을 최대 1.25, 그림자 맵을 512px, 그림자 갱신을 최대 30회/초로 제한한다. 주인공 애니메이션은 렌더 프레임을 따르고 일반 손님은 최대 15회/초, 다른 화면 안 인물은 최대 30회/초로 갱신한다. 화면 밖 인물의 애니메이션은 생략하지만 이동·구매·전투 시뮬레이션은 유지한다. 직업 장식·스택 geometry를 공유하고, 체력바·직업 링은 두 인스턴스 묶음으로 그린다. 이 정책은 실제 휴대폰 자동 벤치마크 결과가 아닌 명시적인 모바일 렌더 예산이다.

전역 성장 21행의 운반량·이동 속도·가격 보너스·강화 비용을 보존한다. 일반 스테이지 10행과 이벤트 정의 1행, 직원 80명의 능력치, 등급 확률 4팩, 선택 시설의 비용·능력도 기존 선택 수치를 유지한다. 표시 이름과 판타지 역할은 새로 만들었다.

현재는 플레이어 성장, 직원 추첨·기본 속도/운반량, 판매 기본값 5/24, 시설 1~3레벨의 비용과 첫 form 능력, 조수 공유 속도/운반 1~11레벨과 기존 훈련 비용을 실제 적용한다. 시설의 다른 form 선택, 스테이지 오프라인 보상 필드·별도 이벤트·직원 `income`의 별도 수익 효과는 아직 적용하지 않는다. 최고 플레이어 성장 행의 비용도 보존하지만 21레벨에서는 더 이상 비용을 지불하지 않는다. 시설·조수의 정확한 단계 매핑과 새 통화 해석은 `data/PROVENANCE.md`에 기록했다.

일반 지역 10곳은 이름뿐 아니라 바닥·장식·시설 위치·문과 동선이 다른 실제 맵이다. 방어 승리로 단계가 오르면 마당에서 결과를 보여 주고, `계속 영업`을 누르거나 규칙의 결과 대기 7초가 지난 뒤 다음 지역 상점으로 돌아온다. 결과 모달이 열린 브라우저에서는 시간이 멈춰 직접 계속을 누른다. 10곳 뒤에는 첫 지역부터 반복한다. 지도 목록에서는 아직 도달하지 않은 지역도 열람할 수 있지만 지역을 선택해 여행하거나 건너뛰는 기능은 없다. 이전 시 소지금·현금 더미·강화·보유 짐·단골을 유지한다. 별도 이벤트 야영지는 정의만 보존하며 플레이 지역으로 열지 않았다.

구매 단골 3명 이상을 확보해야 첫 습격이 시작된다. 판매 18회 또는 영업 90초 후 10초간 준비한다. 판매 8회 뒤 궁수와 연금 공방, 16회 뒤 여관, 20회와 공방 개방 뒤 마법사가 열린다. 시작 금화는 80이며, 조수 동시 상한은 5명이다. 이동 21레벨에서 거리 3.5·대기 4초의 순간이동을 사용한다. 판매 금화 환산과 습격 보상·귀환 방어는 신규 웹게임 규칙으로 기존 비용과 분리했다. 정확한 계산과 조건은 `rules.mjs`, 보존·재해석 범위는 `data/PROVENANCE.md`를 참고한다.

10초 경고가 끝나면 영업과 시간이 멈춘 `마당 방어 준비` 확인창을 보여 준다. `마당으로 출전`을 누르면 2.2초 페이드가 진행되고 중간에 상점 내부 전체를 숨긴 채 건물 밖 마당과 수호대·적을 배치한다. 페이드 동안 이동·생산·판매·공격·피해는 진행하지 않으며, 전환이 끝나야 자동 전투를 시작한다. 야외는 실내 확장과 독립된 고정 좌표를 사용하고 상점 외벽·문·지붕·잔디·흙길·성벽만 보인다. 승리·패배 결과도 마당에서 유지하고, 계속하거나 무료 복구하면 상점으로 돌아온다.

침공은 단계와 최근 구매 단골 최대 18명에 따라 4~32명의 적을 편성하고, 처음 최대 14명이 함께 출현한 뒤 2.2초마다 3명씩 증원한다. 동시 생존 적은 최대 20명이다. 2단계부터 원거리와 정예가 섞이며 돌격병은 후열을 압박한다. 돌격병의 기본 속도는 1.95·사거리는 1.05, 적 궁병 사거리는 3.75다. 궁수·마법사 단골은 후퇴하는 동안 공격하지 않으므로 근접 압박에 대응하려면 앞줄 전사와 장비 성장이 필요하다. 적 체력·공격력·인원은 플레이어 장비·충성도에 맞춰 자동으로 올라가지 않는다. 더 높은 마법 부여 단계의 물건을 산 단골은 공격력·체력이 높고, 여관과 방어 승리의 충성도도 도움이 된다. 결과창에서 방어 시간·전투불능·부상·상회 피해를 확인한다. 전투는 원작에 없는 이 웹게임의 별도 설계다.

무기와 활·지팡이는 실제 모델의 오른손 뼈에 연결하고, 시뮬레이션에서 타격이 발생한 순번(`attackSerial`)이 바뀔 때만 약 0.45초 단발 모션을 재생한다. 공격 대상 쪽으로 몸을 돌리고 타격 후에는 걷기·대기 자세로 돌아간다. 이 연출로 원래 공격 간격·공격력·체력을 바꾸거나 피해를 중복 적용하지 않는다.

## 저장과 호환

저장 키는 `runehaven:v1`이며 이 게임의 데이터만 사용한다. 초기 v1 기록에 시설 단계·조수 공유 훈련·현금 더미 필드가 없으면 각각 1레벨·1레벨·0으로 보완한다. `dining`이 없으면 주방 4그릇·배식대 0그릇으로 보완한다. `tableCount` 없는 이전 저장은 여관이 열려 있으면 기존 식탁 4개를 보존하고, 미개방이면 첫 슬롯 1개만 예약한다. 새 진행은 첫 식탁에서 시작한다. 구매 식탁 수와 식탁별 `cash`를 저장하며, 이전 `moneyPiles.inn` 현금은 기존 위치의 별도 더미로 보존한다. 기존 식사 버전의 저장에 주방 값이 없으면 주방만 4로 채우고 배식대 `food`는 보존한다. 플레이어·조수의 짐에 `food`가 없으면 0으로, 조수 담당이 없으면 기존 운반 품목으로 보완한다. 음식·담당·실제 운반 짐·정리 횟수·좌석 상태를 저장하며 각 식탁의 `seats`가 상태 기준이고 기존 식탁 필드는 표시용 요약이다. 이전 1좌석 기록의 사용·예약·더러운 상태는 첫 자리에 옮기고 두 번째 자리는 새로 보완한다. 불러올 때 고객은 재생성하고 사용·예약 중 자리는 정리가 필요한 상태로 바꾸므로 식사 중 재접속해 매출을 중복 지급하지 않는다. 기존 소지금과 구매·강화 기록은 유지한다. 신규 값이 범위를 벗어나거나 저장 구조가 손상되면 새 상회로 초기화한다. 다른 게임의 저장 데이터는 읽지 않는다.

미완료 주문에서 이미 건넨 물건은 손님 이탈·전투 전환 때 `returnedStock` 환입 대기 재고로 돌린다. 저장할 때도 미완료 손님의 전달분을 대기 재고에 포함한다. 진열·배식대가 가득 차면 수량을 보존했다가 공간만큼 복구하며, 이전 저장에 해당 필드가 없으면 품목별 0으로 채운다. 이는 아직 결제하지 않은 물건의 보존 처리이며 금화 환불이나 완료 주문 매출의 취소를 뜻하지 않는다.

저장 공간 사용이 막히거나 저장에 실패해도 현재 탭의 기본 플레이를 유지한다. 처음부터 시작하면 이 게임의 새 기록으로 덮어쓴다. 출전·전투 중에는 야외 좌표 대신 출전 전 상점 위치와 실제 운반 짐을 저장한다. 이를 불러오면 구매·강화·짐·현금 더미를 유지한 상점의 45초 준비 상태로 돌아간다. 패배 상태를 불러와도 무료 복구 버튼을 제공한다. 저장 키와 버전은 `runehaven:v1`을 유지한다.

### 최신 원본 메시·바닥 원·24×24 매장 — 2026-10-31

원본 APK의 실제 메시 11종을 선별하여 색상·웹 좌표·관절 연결을 변환해 사용한다. 얼굴 없는 손님·모자와 앞치마·카운터·그릴·식탁·의자·버거·컵·포장지·지폐의 원본 면 연결을 검증했다. 원본 T 자세·22본의 압축 가중치는 웹의 8본에 묶었고 원작 클립·셰이더·모든 GameObject 배치를 그대로 옮기지 않았다. 파일별 SHA와 변환 과정은 assets/burger-source/에 있다. 데이터 모듈은 243,710바이트이며 원본 자산과 Kenney CC0를 구분한다.

### 이전 2좌석·복수 주문·시설 몸체·운반 표현 — 2026-10-31

이하 직접 브라우저 검증은 이번 원본 메시·24×24·바닥 원 구매 변경 전 기록이다. 현재 버전의 직접 플레이 검증으로 재사용하지 않는다.

APK의 `Order.FoodOrderSet`·`Stage.InitData`·`OrderBalloonForm.Refresh`를 정적으로 대조해 일반 주문의 기본 1~2개, 활성 식탁 4개마다 추가 1개, 식탁 2개 미만의 1개 분기를 확인했다. 7:00 영상에서도 2개 주문 말풍선·마주 앉은 두 손님·앞손의 음식을 확인했다. 첫 지역 튜토리얼·VIP·전화 주문은 별도 분기이므로 웹의 일반 주문과 구분한다. 상세 RVA·원문 식별자·해시는 `data/APK_SERVICE_REVIEW.md`에 있다.

식탁별 `seats[2]`를 상태 기준으로 바꿔 좌석마다 예약·식사·청소를 관리한다. 주문은 생성 후 고정하고 한 개씩 전달하며, 일반 상품은 완료 때만 수량만큼 결제·단골 1명·판매 1회를 기록한다. 부분 전달 후 이탈·출전·재접속하면 물건을 환입 대기 재고로 보존한다. 이전 1좌석 저장·유료 식탁·누적 대금도 유지한다.

시작 때의 GLB 일괄 사전 로드와 인물별 GLB·애니메이션 복제를 제거했다. 몸은 1 draw·520 triangles·8 bones와 공유 재질로 구성하고, 마법사만 작은 모자 1 draw를 더한다. 식당 가구 GLB 11개도 로드하지 않는다. 식당 가구 자체의 mesh 수는 기본 도형 분리로 늘었으므로 모든 모듈의 draw call이 감소했다고 주장하지 않는다. 실제 주방 운반 화면의 22명 고객·DPR 1 표본은 72 draw calls·11,352 triangles였다. 이전 배포본은 카메라 위치·고객 수가 달라 전체 감소율 비교에서 제외했다.

**18개 지정 테스트 파일의 182개 테스트**, 변경 실행 모듈 6개의 구문 검사와 대상 diff 검사가 통과했다. 새 인물 6개 회귀는 단색·공유 버퍼·높이·걷기·운반·착석·오른손 공격과 실제 무기 정점의 모바일 여백을 검사한다. 착석 발이 바닥 아래로 내려가던 문제를 수정했고 실제 변형 정점으로 재검증했다. 시설 간격도 이전 GLB 치수 대신 실제 새 도형의 Box3로 검사해 10개 지역 최소 0.675, 음식 줄·식탁 최소 0.9를 확인했다. 규칙·성장·판매 수치와 v1 저장 형식은 변경하지 않았다.

브라우저 390×844에서 주방의 음식 2개를 머리 위에 싣고 배식대까지 직접 운반해 소지 음식 0·배식 음식 2가 되는 것을 확인했다. 320×568의 인위적 식당 검사 상태에서는 착석·사용한 식탁을 관찰하고 `식탁 1 정리`를 눌러 정리 0→1·해당 식탁 clean을 확인했다. 인위적 공급 재고를 정상 획득 진행으로 간주하지 않는다.

### 이전 먼 교전 시점 연결 — 2026-10-24

아래 모델·장면·성능 표본은 단색 그래픽으로 바꾸기 전 버전이다. 카메라 정책은 유지하지만 이전 그래픽과 수치를 현재 화면 검증으로 재사용하지 않는다.

고정 배율과 최소 여백을 동시에 지켜야 하는 먼 교대는 두 안전 구도 사이를 0.26초 교차 페이드하도록 바꿨다. 한 프레임의 실제 지면 이동을 CSS px로 투영해 24px를 넘을 때만 시작한다. 일반 추적은 기존 완화를 유지한다. 유효한 원거리 공격은 동작 종료 뒤 0.18초 안정 시간을 주어 교대 왕복을 줄이며, 죽거나 먼 교전은 즉시 해제한다. 선택 정책만 바꾸었고 공격 시각·피해·체력·증원·성장 수치는 유지했다.

화면 저장은 그리기 버퍼 크기의 `FramebufferTexture` 2장을 재사용한다. 전투 중 GPU 복사는 프레임당 1회, 페이드 중에는 화면 사각형 1 draw call·2 triangles만 추가한다. CPU 픽셀 읽기·두 번째 전장 렌더·상시 DOM 덮개는 사용하지 않는다. 재교대는 마지막으로 표시한 합성 화면에서 이어지며, 첫 프레임·크기 변경·출전에는 이전 스냅샷을 표시하지 않는다. 일시 정지에는 페이드 시간도 멈추고, 전투 종료에는 GPU 스냅샷을 반환한다. QA의 실제 프레임 수는 추가 합성 패스 수와 분리했다.

### 이전 시점 교대 여백 보정 — 2026-10-24

아래 165개 테스트·여백 표본은 먼 교대 교차 페이드를 넣기 전 버전의 기록이다.

선택한 공격의 발사자와 표적에 적용한 여백을 실제 렌더 카메라 위치에서도 지키도록 보완했다. 고정 인물 크기를 유지한 채 평소에는 부드럽게 추적하고, 시점 교대 때 여백을 벗어나는 부분만 최소 거리로 보정한다. 최종 화면 검사는 같은 정상 획득 `late-defense` 경로를 사용했다. 아래 160개 테스트와 이전 화면의 여백 부족 관찰은 이전 버전의 기록으로 구분한다.

지정한 16개 테스트 파일의 **165개가 모두 통과**했다(약 2.332초). 카메라 회귀는 32개로, 교대 첫 프레임의 최소 여백·고정 인물 크기·최소 위치 보정·30/60Hz 추적과 가능한 공격 쌍 선택을 확인한다. 변경한 카메라와 화면 연결 모듈의 구문 검사 2개 및 대상 `git diff --check`도 통과했다.

발사자의 보호 범위에는 직업별 무기 동작을 포함한다. 궁수·일반 원거리 공격은 화면 가로 방향 ±0.8, 마법사·몬스터 원거리 공격은 ±0.9, 근접 무기는 ±1.1 월드 단위의 범위를 잡고 아래쪽 투영 여유도 추가한다. 표적은 ±0.6, 높이는 2.6을 기준으로 한다. 같은 배율에 실제 공격 양끝과 최소 여백을 함께 담을 수 있는 쌍을 우선 선택한다. 아직 멀리 접근 중인 경우 등 양끝 보호가 불가능하면 표적만 보호하며, QA의 `subjectFits`·`subjectFramedSource`로 그 범위를 구분한다. 실제 무기와 화살의 geometry 투영 검사는 이 보호 범위 검사와 별도로 확인한다.

최종 **320×568** 후반 전투를 화면 입력으로 진행해 29명의 적을 상대로 11.8609초에 승리했다(전투불능 0명·부상 6명·상회 피해 0). ### 이전 대기열·색상·통로 개선의 검증 기록 — 2026-10-23

아래 82개 테스트·화면 표본·잠정 평가는 동선과 전투를 후속 조정하기 전 버전의 기록이다. 최신 변경의 검증 결과로 재사용하지 않으며, 후속 검증은 별도 기록한다.

규칙·정상 진행·전투·고객 동선·지도·카메라·공유 렌더 자원·실제 GLB 인물 색상의 **테스트 82개가 통과**했다. 실행 모듈 10개와 별도 QA 시나리오 정의 `tests/scenarios.mjs`의 구문 검사도 통과했다. 이번에는 고객의 입장·대기·퇴장·숙박 경로와 인물 색상을 변경했으며 기존 판매 가격·결제시간·직렬화한 v1 저장 형식은 유지했다. 이전 수치 대조 검사 929건의 기록도 변경하지 않았다.

10개 지역을 각각 120초 동안 재고를 통제 보충하며 시뮬레이션한 결과, 지역마다 최대 고객 30명을 기록했고 중앙 영역 `abs(x)<1.25, -2.2≤z≤4.8` 침범은 0건이었다. 첫 20초 이후 지역별 최소 동시 대기는 12~19명, 첫 10초를 제외한 각 10초 구간의 판매는 7~15회였다. 입장과 구매 후 퇴장·여관 이동이 이어지는 중에도 상품별 16명·대기 24명·숙박 4명·전체 30명 상한, 구매 순서·재고·대금 보존을 확인했다. 이 재고 보충 검사는 동선의 지속 처리량을 확인하기 위한 통제 조건이며, 플레이로 획득한 재고나 실기기 성능 측정으로 취급하지 않는다.

재고가 없는 45초 검사에서는 10개 지역 모두 고객 24명이 각자의 FIFO 대기 자리에서 0.04 월드 단위 이내로 정렬됐다. 긴 U자형 한 줄, 꼬리 뒤 자리 예약, 앞 손님 다음으로 전진하는 규칙을 검사해 진열대 앞에 군집하거나 새 손님이 앞 손님을 추월하는 문제를 방지했다. 판매하지 않은 손님이 무료 매출·단골을 만들지 않는 검사와 기존 가격·처리시간을 그대로 쓰는 검사도 통과했다.

390px 브라우저에서 실제 초반 손님 12명, 중앙 바닥을 누른 주인공 이동, 고객의 파란 의상·후드와 주인공의 보라·아이보리 구분을 확인했다. 실제 GPU 모델에서 피부·얼굴·눈 색을 유지했고 두 모바일 크기와 PC 모두 셰이더를 포함한 콘솔 오류·경고는 0건이었다. 색상 도우미는 고객 머리 덮개와 몸통 atlas UV만 바꾸며, 기존 GLB geometry·texture와 같은 셰이더 프로그램을 공유한다. 별도 메시·draw call·매 프레임 색상 재생성을 추가하지 않는다.

`scenario=queues&previewRegion=1`부터 10까지를 320×568·390×844에서 확인한 **20개 조합 모두 24명 전원이 대기했고 중앙 침범·작업장 표식 겹침·가로 넘침은 0건**이었다. 표식은 52×52 CSS px, 한글 Jua 글꼴은 로드 완료 상태였으며 모자 포함 주인공 높이는 각각 약 44.13px·53.78px였다. PC 1280×800에서는 실제 플레이 영역 900×557px·주인공 약 59.63px·모바일 품질 설정 비활성·그림자 맵 1024px·넘침 0건을 확인했다. 390×640으로 높이를 바꿨을 때 플레이 영역 높이는 431px였고 넘침이 없었다. 이 검사는 데스크톱 브라우저의 모바일 크기·포인터 검사이며 실제 iOS·Android 터치 검증을 대신하지 않는다.

진열대 납품 도착점과 모든 고객 대기 자리의 거리가 0.75 이상인지 검사했다. 24명 대기 조건의 브라우저에서 대장간 표식을 눌러 무기 2개를 적재한 뒤 진열대 뒤쪽에 정지 하차했다. 지정 판매 표시는 20에서 22로 증가했고 실제 신규 유료 단골 2명과 무기 매출 100이 생겼다. 수금 전 소지금 80을 유지하다 대금 수거 후 180·무기 매출 더미 0이 됐으며, 숙박 매출 252는 여관 더미에 따로 남았다. 대기열 외형 화면의 렌더 표본은 165 draw calls·24,558 triangles였다. 같은 조건의 이전 기준값이나 실기기 FPS 측정은 없으므로 감소율·FPS 향상을 주장하지 않는다.

QA 경로의 일반 저장 격리를 확인했다. `scenario=late`, `defense`, `defeat`는 시드 42의 정상 이동·판매·수금·강화·전투로 획득한 상태를 재현하며 `artificial:false`다. 네 번째인 `?qa=1&scenario=queues&previewRegion=N`은 `artificial:true`로 표시한 대기열 외형 검사다. 시설·판매 횟수 20·지역을 지정한 뒤 실제 고객 이동을 45초 시뮬레이션해 미구매 손님 24명을 세운다. 생성 직후 획득 매출 0·구매 단골 0·골드 80이며, 지정한 판매 횟수를 플레이로 획득한 진행이나 실제 수익으로 취급하지 않는다. 생성 후 직접 납품해 발생한 구매·매출은 위 실제 조작 검사와 구분해 기록했다.

`qa=1&previewRegion=1`부터 10까지와 `scenario=late&previewRegion=N`도 단계 지정 외형 검사이며, `qa=1&previewCargo=gear`, `potion`, `mixed`는 운반량을 21레벨·짐 22개로 지정한 외형 검사다. 이런 지정 조건을 실제 플레이로 획득한 진행으로 보고하지 않는다. 이전 버전의 전투 시간·렌더 호출 표본은 이번 변경의 측정값으로 재사용하지 않았다.

## 출처와 라이선스

Burger Please!를 생산·운반·판매·강화 규칙의 이해를 위한 참고 게임으로 삼았다. 판타지 역할·통화·시간의 적용 방식과 웹게임에서 별도로 만든 규칙은 `data/PROVENANCE.md`에 정리했다. 사용자의 요청에 따라 선택 원본 메시 11종은 색과 웹 좌표·관절 연결을 변환해 사용한다. 원본의 코드·이미지·음원은 반입하지 않았으며 단골 별·강화 화살표 아이콘은 직접 작성한 SVG다. 원본 메시의 독점 자산 표시와 이전 Kenney CC0 라이선스를 구분한다.

이미지·모델·아이콘·효과음·글꼴의 팩 이름, 원본 URL, 라이선스, 사용 파일과 가공 사항은 `assets/SOURCES.md`에 기록하고 필요한 라이선스 파일을 해당 폴더 안에 보관한다. 게임 규칙을 참고한 것과 실제 사용하는 별도 리소스의 출처·라이선스는 구분한다.
