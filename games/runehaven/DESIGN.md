# 룬빛 상회 제작 설계

## 목표와 이번 범위

휴대폰 세로 화면에서 캐릭터를 직접 움직이며 대장간·잡화점·연금 공방·여관을 운영한다. 물건을 생산해 머리 위로 쌓아 나르고 진열대에 공급한 뒤, 가게에 쌓인 현금을 직접 회수한다. 마법으로 운반량·이동 속도·상품 가치를 성장시킨다. 구매한 손님은 모험을 떠났다가 습격 때 돌아와 상회를 지킨다. 마지막 이동 강화는 짧은 순간이동으로 바뀐다.

이번 이정표는 하나의 독립된 웹게임으로 생산→운반→판매→강화→손님 확장→귀환 방어→회복/재도전 흐름까지 실제 플레이 가능하게 만드는 것이다. 아래 계획은 완료 확인 기준을 포함하며, 후속 아이디어를 구현 완료로 표시하지 않는다.

## 제작 순서와 완료 조건

| 단계 | 구현할 내용 | 완료 확인 |
| --- | --- | --- |
| 1. 데이터 경계 | 선택한 원문 수치와 별도 판타지 규칙 분리, 출처·해시·필드 매핑 보관 | 21개 성장·11개 스테이지·직원 80명·확률 4팩·선택 시설 수치가 원문과 일치 |
| 2. 상회 코어 | 세로 화면의 입체 플레이 공간, 바닥 탭/가상 조이스틱 이동, 생산·운반·진열·결제 | 키보드 없이 손가락만으로 첫 생산과 첫 판매 수행 |
| 3. 성장과 확장 | 원문 성장 비용, 전사→궁수→마법사 손님, 공방/여관, 물리적으로 이동하는 조수 | 강화가 실제 이동·짐·매출에 반영되고 조건 달성 시 시설/손님 개방 |
| 4. 귀환 방어 | 구매 손님을 귀환 전력으로 축적, 몬스터/외적 습격, 전사·궁수·마법사 역할 구분 | 출정한 손님이 돌아와 전투하고 승리·패배·회복·재시작이 막히지 않음 |
| 5. 마법과 검증 | 단계별 마법 피드백, 이동 21레벨 순간이동, 저장·일시 정지·도움말 | 순간이동 거리/대기시간·탭 복귀·저장 실패·320~390px/PC 입력 검증 |

현재 구현은 정지 순차 상하차·직접 수금·시설 1~3레벨·조수 공유 1~11레벨·일반 지역 10곳과 승리 즉시 이전에 고객 대기열·역할별 인물 크기·부대별 습격을 연결한 상태다. 여관은 주방에서 조리한 음식을 머리 위에 쌓아 배식대로 나르고, 손님이 식탁에 앉아 먹은 뒤 주인공이나 정리 담당 조수가 사용한 자리를 정리한다. 조수에게 무기·물약·음식 운반 또는 식탁 정리를 지정할 수 있다. 이동 중 겹침을 허용하고 모든 영업 이동은 목표까지 직선으로 처리한다. 규칙 테스트, 브라우저 플레이, 실기기 성능 검증은 서로 구분한다. 최신 검증 명령·결과·미검증 항목·자체 평가는 [README](README.md)를 기준으로 하며 초기 버전의 평가를 현재 상태에 재사용하지 않는다. 원작 화면·영상 관찰과 정지 0.4초 같은 새 구현값의 구분은 [RESEARCH](RESEARCH.md)를 참고한다.

## 기본 플레이

플레이어는 작업점에서 0.4초 멈춘 뒤 0.22초 간격으로 물건을 하나씩 싣고 내린다. 이동을 재개하면 정지 대기를 다시 시작한다. 구매 손님은 바로 떠나거나 개방된 여관에서 식사한다. 매출은 무기·포션·여관의 각 현금 더미에 쌓인다. 소지금으로 쓰려면 더미 0.9 이내로 접근해 수거해야 하며 이 수거에는 정지 대기가 없다. 방어 보상만 즉시 소지금으로 지급한다. 충분한 운반량이 없으면 한 번에 옮길 수 있는 양이 줄고 진열이 비면 판매가 멈추므로 이동·수금과 조수 고용 시점이 실제 운영 선택이 된다.

진열대 표식이나 시설 가까운 바닥을 눌러 자동 이동할 때는 `getStationApproach`의 도착점을 사용한다. 무기·물약 납품은 해당 진열대 뒤쪽 `station.z - 0.85`로 이동해 손님이 결제하는 앞줄과 분리하고, 대장간·연금 공급기는 기존 `station.z + 0.8`을 사용한다. 직접 조이스틱 이동은 자유롭게 유지한다. 정적 동선 검사는 모든 지역의 두 상품 대기열 슬롯과 자동 납품 도착점 사이 거리 0.75 이상을 대상으로 한다.

작업장·대금·식탁 표식과 바닥 탭은 목표 한 점까지 직선으로 이동한다. 플레이어의 이동 정지 기준은 0.08이며 경유점 배열이나 대기열 충돌 검사를 만들지 않는다. 손님·조수와 겹쳐도 이동을 중단하거나 돌아가지 않는다. 진열대 뒤의 납품 도착점은 시각적 역할 구분을 위해 유지한다.

조수도 실제로 움직여 하나씩 싣고 내리며 플레이어와 같은 작업점을 공유한다. 담당은 `gear`·`potion`·`food`·`clean` 중 하나이며 `assign-worker`의 `{ id, job }`로 지정한다. 무기·물약은 생산기와 진열대, 음식은 주방과 배식대 사이를 원문에서 적용한 속도로 직선 이동한다. 정리 담당은 더러운 식탁으로 걸어가 1.2초 작업한다. 담당을 바꿔도 이미 든 짐은 원래 납품점에 먼저 내려놓은 후 새 일을 시작한다. 조수별 자리 배정·경로 캐시·양보 대기 없이 겹침을 허용하고, 기존 생산·운반량·상하차 시간과 고용 비용은 유지한다. 핵심 행동은 플레이 공간 안에서 이루어지고 상세 설명·설정은 접을 수 있는 메뉴에 둔다.

직무 변경은 `helper.job`에 즉시 기록하되 현재 짐의 품목을 우선 납품한다. 별도의 대기 직무를 만들지 않고, 정리 담당으로 바꿀 때 `helper.product`에는 이전 운반 품목을 남긴다. 실제 납품 대상은 짐의 품목으로 정하므로 음식 운반 중 다른 담당으로 바꾸거나 저장 후 다시 열어도 짐을 잃지 않는다. 직접 맡긴 담당에는 선택 표시 `jobAssigned`를 두어 연금 공방 개방 시의 기본 물약 담당 전환이 사용자의 지정을 덮어쓰지 않게 한다.

예외로 정리 담당이 기존 짐을 들고 있으나 그 납품처가 가득 찼다면 먼저 더러운 식탁을 정리한다. 특히 모든 식탁이 더러워 손님이 배식대 음식을 가져가지 못하는 상황에서 납품만 기다려 멈추지 않게 한다. 납품처에 빈자리가 생기면 보존한 짐부터 내려놓고 정리를 이어간다. 음식 수량이나 매출을 임의로 늘리거나 짐을 버리지 않는다.

첫 손님은 전사다. 판매 8회 뒤 궁수와 연금 공방, 16회 뒤 여관, 20회와 공방 개방 뒤 마법사가 등장한다. 조건 숫자는 새 웹게임 규칙이며 원작 추출값으로 설명하지 않는다. 손님 직업은 구매 품목과 방어 역할을 연결한다. 전사는 앞에서 버티고 궁수는 뒤에서 공격하며 마법사는 마법으로 광역 압박을 보조한다.

시작 금화는 80이다. 이번 시작 배치의 대장간·진열대는 이미 개방되어 있다. 원문 생산기 비용 50은 선택 데이터에 보존하되 초기 골드에서 공제하지 않는다. 조수 고용 비용은 원문 배열의 0·450·700을 사용한다. 화면과 경로가 혼잡해지지 않도록 이번 버전의 동시 조수 상한은 3명으로 정한다. 원문 `workerMaxEmploy=5`는 데이터에 보존하고 이 차이를 출처 문서에 기록한다.

## 손님 수와 매장 동선

입장·대기 중인 손님의 목표 인원은 `min(24, 12 + (판매 8회 이상 ? 2 : 0) + (공방 개방 ? 4 : 0) + (여관 개방 ? 6 : 0))`이다. 시작 목표는 12명, 시설을 모두 열면 24명이며 입장·대기·식사·퇴장 중 손님을 합한 전체 상한은 30명이다. 목표 인원이 즉시 생성되는 것은 아니며 도착 간격에 따라 늘어난다.

무기와 물약은 매장 좌우에 각각 최대 16자리의 긴 U자 대기열을 가지며, 먼저 입장한 손님부터 결제하는 FIFO를 유지한다. 맨 앞은 해당 카운터에서 `z + 0.65`, 중앙 쪽으로 0.65 이동한 위치이되 `abs(x) >= 2.9`를 지킨다. 여기서 입구 방향의 `z = 4.45`까지 줄을 늘리고 바깥쪽 `abs(x) = 5.1`로 꺾은 뒤 매장 뒤쪽으로 돌아가는 대기 자리를 배치한다. 이 U자는 도착 후 서 있는 줄의 모양이며 이동 경로가 아니다. 새 손님과 다음 순서를 기다리는 손님은 현재 FIFO 번호에 해당하는 자리까지 직선으로 움직인다.

이동 손님끼리 겹치거나 먼저 목표 근처를 지나는 것은 허용하지만 앞 고객이 결제하기 전 뒷 고객이 결제하지 않는다. 배식 줄·식탁·출구도 목표 한 점으로 직접 이동한다. 고객 밀어내기 반복·중앙 영역 진입 제한·별도 입퇴장 우회선은 제거했다. 따라서 대기열 모양은 읽기 쉽게 유지하면서 이동 계산은 인원수에 따라 한 번씩 처리한다.

대기열 맨 앞에 도착한 손님만 현재 진열대의 결제 시간 2 / 1.5 / 0.9초를 채워 구매한다. 도착 간격은 `clamp(결제 시간 / (공방 개방 ? 2 : 1) × 0.75, 0.3, 1)`초이며, 대기자가 6명 미만이면 최대 0.65초로 줄여 빈 매장을 채운다. 이번 동선 변경은 이 도착 간격·고객 목표·전체 상한·원문 결제 시간·가격을 바꾸지 않는다. 실제 첫 구매와 다음 구매까지는 대기 자리로 걷는 시간이 추가된다. 90초를 넘게 기다린 미구매 고객은 포기를 표시하고 맨 앞에 도착한 뒤 출구로 바로 떠난다.

여관의 배식 줄·식탁으로 이동·식사 중인 손님은 합쳐 최대 4명이다. 여관이 열려 있고 이 상한에 여유가 있으면 구매 고객의 60%가 배식 줄로 향한다. 새로 온 순서로 배식대 앞에 서며, 맨 앞 손님은 깨끗한 식탁과 음식 1그릇이 모두 있을 때 음식을 받아 식탁을 예약한다. 예약한 식탁까지 음식을 들고 직선 이동해 앉은 다음 식사 시간을 센다. 모든 고객 수·배치 간격·선택 확률은 새 웹게임 설계로 원작 영상에서 측정한 숫자가 아니다.

### 여관 식사와 식탁 정리

`dining.mjs`는 지역별 주방·배식대·4개 식탁·좌석·정리 접근점과 새 운영값을 정의한다. 주방 음식 `dining.kitchen`은 최초 4그릇, 여관 개방 후 3초마다 1그릇씩 최대 8그릇까지 조리한다. 배식대 음식 `dining.food`는 새 게임에서 0이며 실제 납품으로만 늘고 상한은 8그릇이다. 주방과 배식대의 중심은 2.7 떨어져 있어 한자리에 서서 받고 내릴 수 없다. 주인공은 0.4초 정지 뒤 0.22초마다 1그릇씩 싣거나 내리고, 무기·물약·음식의 공통 운반량을 초과하지 못한다. 운반 중 음식은 다른 상품처럼 머리 위 스택에 보인다. 음식 담당 조수도 같은 재고를 실제로 나르며 보이지 않는 재고 전송을 하지 않는다.

원문 여관 시설의 단계별 시간 5 / 4.7 / 3.7초를 식사 시간으로, 가격 24와 단계별 보너스를 식사 수입으로 재해석한다. 주방·배식대 분리와 음식·식탁 수·조리·정리 시간·조수 직무는 새 웹게임 규칙이다.

식사가 끝나면 여관 대금 더미에 매출을 남기고 해당 단골의 체력을 완전히 회복하며 충성도를 1 올린다. 손님은 퇴장하고 식탁에는 사용한 그릇이 남아 `dirty`가 된다. 주인공이 정리 접근점 1.1 이내에서 1.2초 연속 정지하거나 정리 담당 조수가 접근해 같은 시간 동안 작업하면 그 식탁만 `clean`으로 바뀐다. 주인공이 이동하면 자신의 정리 진행을 초기화한다. 더러운 식탁은 새 손님에게 배정하지 않으므로 직접 정리하거나 조수의 담당을 바꾸는 선택이 식탁 회전율에 영향을 준다.

식탁은 `clean → reserved → eating → dirty → clean`으로 바뀐다. 습격으로 대피하면 예약만 한 자리는 비우고 식사 중인 식탁은 더럽힌다. 식사 시간을 채우지 않은 손님에게 식사 매출·회복 보상을 지급하지 않는다. 지역 이전은 새 식탁 배치를 사용하며 주방·배식대 음식과 누적 정리 횟수는 보존한다. v1의 선택 필드 `dining`에 주방·배식대 재고·정리 횟수·식탁 상태를 보존하고, 플레이어·조수 짐의 `food`와 조수 직무도 보존한다. 고객 예약은 재생성하고 불러온 비어 있지 않은 식탁은 정리가 필요한 상태로 바꿔 중복 보상을 막는다. 이전 v1에 주방이 없으면 4, 짐의 음식이 없으면 0, 조수 직무가 없으면 기존 운반 품목으로 보완하며 기존 배식대 `food`는 그대로 둔다. 식사 필드 자체가 없던 저장은 주방 4·배식대 0으로 시작한다. `dining-visuals.mjs`가 음식·식기와 착석·사용 후 상태를 공유 리소스로 표현한다.

새 고객의 직업을 한 번 뽑은 뒤 해당 상품 줄이 가득 차 있으면 그 선택을 `pendingCustomerKind`로 유지한다. 다른 상품 줄에 빈자리가 있다는 이유로 마법사 등 다른 직업으로 바꾸지 않으며, 원래 직업이 입장하면 다음 선택을 한다. 이 보류 값은 일시적인 고객 유입 상태로 저장 형식에 추가하지 않는다. 대기 목표 24명은 상한과 별개인 목표이므로 상품별 16자리 제한과 직업 선택에 따라 무재고 대기는 20~24명일 수 있다.

## 성장과 방어의 연결

성장은 이동·운반·가격 세 축이다. 전역 21행의 원문 수치와 비용을 보존하며 선택한 현재 레벨의 효과와 다음 비용을 함께 보여준다. 이동 수치의 마지막 원문 값은 6이고, 이동 21레벨에는 별도의 신규 능력인 거리 3.5·대기 4초의 순간이동을 연다. 값싼 초기 성장은 바로 체감하고 높은 후반 비용은 운영 확장과 방어 보상으로 이어지게 한다.

일반 판매는 `(기본 가격 + 원문 price) × 스테이지 환산 배수`를 반올림해 계산한다. 기본 가격은 원문 표현값 5/24를 판타지 품목과 서비스에 차용하며, 환산 배수는 10·25·80·240·750·1500을 시작점으로 쓴다. 이후 승리마다 1.5배를 적용하고 최대 10,000으로 제한한다. 여관 수입은 `24 × 같은 배수 × (1 + 현재 시설 단계의 보너스/100)`을 반올림한다. 두 매출 모두 현금 더미에 적립한 뒤 직접 회수한다. 원문 수치를 고치지 않고 새 수익 환산을 별도로 둔다.

구매 단골 3명 이상을 모은 뒤 판매 18회 또는 영업 90초 조건에 따라 첫 습격을 10초간 준비한다. 단골이 3명 미만이면 시간이 지났어도 습격은 시작하지 않는다. 구매 이력이 있는 최근 단골 중 최대 18명이 방어에 참여하고 홀수 단계는 몬스터, 짝수 단계는 외적이 습격한다. 첫 다섯 차례의 방어 성공 보상은 3,000·8,000·24,000·72,000·216,000이며 이후에는 두 배씩 증가하되 1,000,000으로 제한한다. 승리하면 상회 체력을 최대 40만큼 회복하고 다음 단계로 넘어간다. 패배 시 현재 재화·강화는 유지하며 무료 복구 뒤 다시 준비한다. 실제 계산·시간·상한·입력 검증은 `rules.mjs`의 구현과 테스트를 기준으로 한다.

### 수호대 성장

아래 전투 수치는 새 웹게임 규칙이며 원작 추출 데이터가 아니다.

| 직업 | 기본 체력 | 기본 공격력 | 사거리 | 이동 속도 | 공격 간격 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 전사 | 90 | 15 | 1 | 1.65 | 1.05초 |
| 궁수 | 60 | 12 | 3.5 | 1.6 | 0.85초 |
| 마법사 | 55 | 22 | 3.1 | 1.4 | 1.65초 |

손님이 구매할 때 현재 가격 강화 단계를 그 단골의 `equipmentLevel`로 기록한다. 이후 가격 강화를 해도 이미 출발한 단골의 장비 단계를 소급해 바꾸지 않는다. 전투 공격력은 `기본 공격력 × (1 + (장비 단계 - 1) × 0.1 + min(9, 충성도 - 1) × 0.08)`이다. 최대 체력은 `기본 체력 × (1 + (장비 단계 - 1) × 0.03)`, 출전 체력은 `전투 최대 체력 × max(0.65, 저장된 단골 체력 / 단골 기본 최대 체력)`으로 계산한다. 장비의 공격 보너스와 충성도 보너스는 같은 합 안에 더한다.

첫 구매 충성도는 1이고 식사 완료와 방어 승리 때 각각 1씩 증가한다. 전투 뒤 체력 비율은 단골 기록에 반영하며, 여관 식사 완료 시 해당 단골은 완전히 회복한다. 여관을 연 상태에서는 전투 이외의 운영 단계에 5초마다 모든 단골 체력을 8, 상회 체력을 2씩 회복한다. 마법사는 목표 1.4 이내의 적을 최대 3명까지 공격하고 궁수·마법사는 적이 사거리의 53% 안으로 접근하면 뒤로 물러난다. 후퇴한 틱에는 공격하지 않되 공격 대기 시간은 계속 줄인다. 적이 따라잡아도 후퇴와 공격을 동시에 반복해 피해 없이 이기는 흐름을 막고, 전사 앞줄과 새로 구매할 단골의 장비 성장에 의미를 둔다.

### 적 병력과 역할

지역 단계 `S`, 출전 단골 수 `N`에 대해 적 총원은 `min(32, 4 + min(12, S - 1) × 2 + max(0, N - 3))`이다. 총원은 4~32명이며 첫 출현은 `min(14, max(3, ceil(총원 × 0.65)))`명이다. 남은 적은 2.2초마다 최대 3명씩 증원한다. 살아 있는 적이 18명 미만일 때 묶음 증원을 시작하므로 순간 최대는 20명이다. 장비 강화를 올렸다고 적 체력·공격력이 함께 오르는 방식은 사용하지 않는다.

| 적 역할 | 체력 배수 | 공격 배수 | 기본 이동 속도 | 사거리 | 공격 간격 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 보병 `grunt` | 1 | 1 | 1.05 | 0.95 | 1.25초 |
| 돌격병 `raider` | 0.8 | 1.15 | 1.95 | 1.05 | 1.05초 |
| 궁병 `ranged` | 0.72 | 0.85 | 0.95 | 3.75 | 1.65초 |
| 정예병 `elite` | 2.3 | 1.65 | 0.9 | 1.15 | 1.5초 |

적 체력은 `(108 + S × 12) × 역할 체력 배수`, 공격력은 `(9 + S) × 역할 공격 배수`, 이동 속도는 `역할 기본 속도 + min(S - 1, 8) × 0.03`이다. 0기반 출현 순번에서 2단계 이상은 7의 배수 자리에 정예병, 같은 단계의 나머지 중 5로 나눈 나머지가 1인 자리에 궁병을 배치한다. 그 밖에는 4로 나눈 나머지가 3이면 돌격병, 아니면 보병이다. 후열 압박 조정에서는 이 체력·공격력·총원·증원 시간과 원문 경제 수치를 그대로 유지했다.

돌격병은 후방 궁수·마법사를 우선하며 기회가 나면 상회로 침투한다. 궁병은 거리를 벌리며 투사체로 공격하고 정예병은 가까운 수호대원을 최대 2명까지 함께 타격한다. 상회에는 공격력의 1.5배를 적용한다. 아군·적 화살과 마법 및 해당 투사체의 타격 효과는 색으로 구별한다. 출현은 문 앞의 유한한 빈 위치를 고르고 같은 편 사이에는 반지름 0.46의 분리를 반복 적용한다. 특정 차수의 승리·패배를 고정 연출로 정하지 않으며 구매한 단골·장비·충성도·상처·적 구성에 따라 실제 전투 결과가 달라진다.

## 원문 데이터의 실제 사용

직원 80명은 숫자 ID·등급·운반량·속도·수익·개방 스테이지를 그대로 유지하고 표시 이름을 바꾼다. 웹 고용에서는 현재 스테이지에 따라 원문 확률팩 `min(4,1+floor((stage-1)/3))`을 선택하고, 해당 등급의 개방된 직원 중 한 명을 뽑는다. `income`은 저장된 조수 정보에 복사하지만 별도의 수익 배수로 사용하지 않는다. 이는 원작 가챠 자료를 웹 고용 방식으로 재해석한 규칙이다.

시설은 첫 스테이지 생산기 2종·카운터·테이블·고용의 원문 비용과 연결 능력값을 보존하고 다음과 같이 적용한다. 시설 각 단계의 첫 form에서 type 10을 시간, type 30을 적재량, type 20을 여관 매출 보너스 %로 해석한다.

| 시설 | 1→2 / 2→3 비용 | 1 / 2 / 3단계 효과 |
| --- | --- | --- |
| 대장간 | 120 / 1,990 | 생산 시간 3 / 2 / 1초, 재고 한도 4 / 10 / 14 |
| 잡화점 | 100 / 1,750 | 결제 시간 2 / 1.5 / 0.9초 |
| 연금 공방 | 330 / 2,090 | 생산 시간 3 / 2 / 1초, 재고 한도 4 / 10 / 14 |
| 여관 | 370 / 1,200 | 식사 시간 5 / 4.7 / 3.7초, 매출 보너스 0 / 0 / 5% |

공방 최초 개방 230·여관 5, 조수 고용 0·450·700도 원문 배열을 사용한다. 시설 강화는 현재 레벨 `L`에서 원문 비용 배열의 0기반 인덱스 `L`을 지불하고 다음 레벨로 간다. 첫 비용 인덱스 0은 최초 개방 의미로 보존하며 시작부터 열린 대장간/잡화점에서는 공제하지 않는다. 각 단계의 다른 form은 보존하지만 선택 기능은 없다.

조수 공유 훈련은 속도·운반 각각 1~11레벨이다. `현재 직원 원문 속도 × worker.speeds[L-1] / worker.speeds[0]`, `직원 원문 운반량 + worker.capacities[L-1] - worker.capacities[0]`를 모든 고용 조수에게 적용한다. 훈련 비용은 원문 배열 `costs[L-1]`의 10개 숫자를 그대로 사용한다. 원문 비용 코드 0·54와 시설 코드 1은 이 웹게임에서 모두 금화로 재해석하며, 원작의 각 통화를 같다고 주장하지 않는다.

스테이지의 오프라인 보상 필드와 별도 이벤트 정의는 여전히 실행 기능이 아닌 보존 범위다. 사용하지 않는 원작 43개 전체 테이블·광고/결제 설정·대형 원본 리소스를 실행 페이지에 적재하지 않는다. 런타임 수치에는 조사용 출처 필드를 넣지 않으며 `data/provenance.json`에 원본 파일·행·ID·필드를 분리한다.

## 실제 지역과 진행

`maps.mjs`는 햇살 장터·단풍 광장·별빛 항구·은빛 산길·구름 초원·서리 성문·달숲 마을·붉은 사막·수정 계곡·룬빛 왕도의 10개 배치를 제공한다. `map-scene.mjs`는 각 지역의 바닥 패턴·지형·장식·색과 배치를 그린다. 시설·출입구·플레이어 시작점과 수금 위치·손님/조수 동선도 현재 지역을 따른다.

중앙 보행 공간의 경계는 모든 지역에 `x = ±1.2`, 중심 `z = 1.4`, 길이 7.4·폭 0.07의 얇은 가이드 두 줄로 표시한다. 높이 0.016의 정적 box 두 개를 `y = 0.125`에 놓고 그림자를 끈다. 바닥색에 지역 강조색과 흰색을 옅게 섞어 달숲의 원형 무늬 같은 기존 바닥 특징을 유지하며, 새로운 텍스처나 넓은 덮개 면을 추가하지 않는다.

방어 승리로 단계가 올라가는 즉시 다음 지역으로 이전하고 10개 지역 뒤에는 반복한다. 기존 소지금·현금 더미·짐·시설/조수 강화·단골은 유지하며, 방문 중이던 임시 손님은 정리하고 플레이어와 조수를 새 작업 동선에 배치한다. 지도 목록은 미개방 지역도 읽을 수 있는 목록이며 자유 여행·지역 선택 개방 기능은 아니다. 별도 이벤트 야영지는 아직 플레이 지역이 아니다.

외형 검사용 `?qa=1&previewRegion=1`부터 `?qa=1&previewRegion=10`까지는 새 상태의 `stage`만 지정한 인위적 미리보기다. 정상 규칙으로 획득한 `late`·`defense`·`defeat` 시나리오나 실제 지역 승리 진행과 구분하며, 위 시나리오·지역 미리보기 경로는 일반 저장을 읽거나 쓰지 않는다.

`?qa=1&scenario=queues`는 별도의 인위적 대기열 외형 검사다. 지역·판매 플래그 20·공방/여관 개방·시설 3단계를 직접 지정하고, 무재고 상태에서 정상 고객 동선을 45초 실행해 24명이 대기하는 장면을 만든다. `previewRegion=1`부터 `previewRegion=10` 중 하나를 함께 지정해 지역별로 확인할 수 있다. 단골 0명·획득 매출 0·금화 80인 검사 상태로 정상 구매·강화 진행을 증명하는 시나리오가 아니며, 일반 저장을 읽거나 쓰지 않는다.

`?qa=1&scenario=dining&previewRegion=N`도 인위적인 외형·정리 검사다. 위 대기열 장면에 무기 12개·물약 8개·배식대 음식 4그릇을 지정하고 실제 구매·배식·이동·식사 규칙을 실행해 식사 중 손님과 더러운 식탁이 함께 나타나는 시점에서 시작한다. 그 재고와 개방 상태를 정상 플레이로 획득한 것으로 보고하지 않는다. 초기 장면 이후 주방 음식 운반과 식탁 정리는 화면 입력으로 별도 확인하며 일반 저장은 읽거나 쓰지 않는다.

## 화면과 조작 기준

- HUD·플레이 영역·핵심 행동을 한 화면에 배치한다. 주요 숫자는 28~40px, 버튼과 상태는 18~22px, 본문은 16px 이상을 목표로 한다.
- 휴대폰의 터치만으로 시작·운영·강화·방어·일시 정지·재시작할 수 있어야 한다. 버튼 터치 영역은 최소 44×44px이다.
- 건물·캐릭터·진열품·버튼에 두께·광원·그림자·눌림·운반 반응을 준다. 얇은 글씨와 작은 영문 캡션 위주의 상태판을 플레이 화면에 두지 않는다.
- 화면 높이 변화·안전 영역·숨겨진 탭 복귀를 처리한다. UI가 조작 영역과 핵심 경고를 가리면 완료로 보지 않는다.
- 인물의 기준 배율은 주인공 1, 일반 손님 0.72, 조수 0.92, 귀환 수호대 0.9다. 적은 보병 0.95, 돌격병·궁병 0.9, 정예병 1.22로 구분한다. 같은 직업이라도 일반 손님과 전투 단골의 역할을 분리하고 몸·장식·짐을 함께 확대·축소한다. 이 비율은 원작에서 측정한 수치가 아니다.
- 인물 색은 기존 Mini Dungeon 아틀라스의 의상·장식 UV 띠를 셰이더에서 다시 선택한다. 주인공은 보라·아이보리, 일반 고객은 파랑 의상과 파랑 머리 덮개, 조수는 금색·아이보리, 수호대는 초록 계열, 적은 붉은 계열로 구분한다. 고객 머리 덮개 이외의 피부·얼굴·눈 영역은 유지하며 원본 텍스처·geometry·스켈레톤을 바꾸지 않는다. 기존 개체별 재질에 셰이더 uniform만 적용하므로 색 구분용 메시·텍스처·추가 그리기 호출을 만들지 않는다.
- 전투 중 일반 손님과 조수는 몸·짐·표식을 숨기고 애니메이션을 생략해 대피를 표현한다. 손님은 식사를 취소하고 출구로 향하며 사용 중 식탁은 정리가 필요한 상태가 된다. 기존 구매·재고·조수의 운반 짐은 유지하고 영업 복귀 시 비전투원을 다시 표시한다.
- 영업 카메라는 `min(46, 화면 폭 / 9.4, 짐 높이에 따른 안전 배율)` CSS px/world unit을 기준으로 플레이어를 추적한다. 가장자리 제한·높은 짐의 자동 줌·점멸/지역 이전 시 스냅을 적용한다. 전투는 별도 구도로 플레이어·살아 있는 부대·문 앞 생성 영역을 함께 담으며 종료 후 영업 구도로 복귀한다. 이 카메라 수치는 신규 웹게임 설계다.
- 첫 매장은 14×13 공간에 7×26개의 판재 바닥을 그리며 뒤벽 상단은 1.9, 줄서기 바닥 표시는 상품별 16개씩 최대 32개다. 표시 위치는 고객 대기열과 같은 규칙 함수를 사용한다. 모든 지역에서 플레이 좌표와 시설 좌표를 함께 유지한다.
- 모바일 렌더는 DPR 최대 1.25·512px 그림자·최대 30Hz 그림자·일반 손님 15Hz/주변 인물 30Hz 애니메이션 예산을 사용한다. 화면 밖 인물 애니메이션은 생략하고 시뮬레이션은 유지한다. 직업 장식과 스택 geometry를 공유하며 인스턴스 수량만 갱신한다. 체력바와 역할 링은 각각 최대 80개의 인스턴스를 갖는 기존 InstancedMesh 두 개를 재사용하고 퇴장·사망 인물을 제거한 뒤 수량과 행렬을 갱신한다. 실기기 FPS·발열 측정은 별도 검증 항목이다.
- 시작 화면과 일시정지 메뉴 양쪽에 `진행 초기화`를 둔다. 확인 창의 취소·X·Escape는 처음 진입한 화면으로 돌아가며, 확정하면 골드·시설·강화·조수·단골·지역 진행을 새 상태로 저장하고 즉시 시작한다.

## 후속 확장 후보

별도 이벤트 야영지, 시설의 추가 form 선택, 자유 여행·지역 선택 개방, 여관 방 배정과 생활 일정, 원문 오프라인 보상 적용, 직원 도감과 상세 고용 연출, 더 많은 적 전술과 수비대 편성은 후속 확장 범위다. 현재 구현한 일반 지역 10곳·시설 3단계·조수 공유 11단계·음식 운반과 조수 직무 지정을 이 후속 목록과 혼동하지 않는다. 여관에는 음식 운반·식사 수입·회복·식탁 정리가 있으며 생활 일정이나 숙박 방 배정은 없다.
