# 참고 게임과 웹게임 수치의 적용

Burger Please!는 생산·운반·판매·강화와 매장 운영 규칙을 이해하기 위한 참고 게임이다. 영상만으로 파악하기 어려운 동작과 규칙을 이해하는 데 참고했으며, 원작 코드·이미지·음원은 사용하지 않으며, 2026-10-31 원본 그래픽 재사용 요청에 따라 선택 원본 메시 11종을 색·웹 크기·관절 연결을 변환해 사용한다. `source-balance.mjs`는 웹게임에 적용하는 선택 수치를 정리한 모듈이다.

## 규칙 설계에 참고한 수치 영역

| 데이터 | 웹게임의 구성 범위 |
| --- | --- |
| 플레이어 성장 | 21행의 레벨·운반량·속도·가격 보너스·각 비용 |
| 스테이지 | 일반 10행·이벤트 1행의 ID·재화 단위·오프라인 보상 관련 값 |
| 직원 | 80명의 ID·등급·운반량·속도·수익·개방 스테이지 |
| 등급 확률 | 팩 4종×등급 4종 |
| 시설 | 첫 스테이지의 생산기 2종·카운터·테이블·고용 비용과 연결 능력, 식탁 1~4의 개별 개방 비용·각 2좌석 |
| 기본 가격 | 5와 24 |
| 조수 성장 | 운반량·이동 속도·최대 고용 5·속도/운반/고용 비용·기존 자원 식별자 |

선택 수치의 소수 표현과 비용 곡선은 기존 구성을 유지한다. 참고 수치와 웹게임에서 별도로 정한 규칙을 구분하며, 숫자·배열·검증 기록은 이번 문서 정리로 변경하지 않는다.

## 이 웹게임에서 바꾼 의미

- 생산기 → 대장간/연금 공방, 카운터 → 잡화점, 테이블 → 여관, 고용 → 조수 길드로 바꿨다. 스테이지와 직원의 표시 이름은 판타지 이름으로 새로 붙였다.
- 현재 시설 코드 1과 조수 훈련 코드 0·54의 선택 비용은 모두 웹게임 금화로 지불한다. 코드 숫자만으로 참고 게임의 특정 통화라고 단정하거나 현재 별도 룬 결제 자원이 있다고 설명하지 않는다.
- 기본 가격 표현 값 5/24를 무기·포션·여관 서비스의 기본 가격으로 차용했다. 역할과 품목은 새 설계이며, 판매 금화 환산은 `balance.mjs`의 `WEB_RULES.saleCoinMultipliers`와 `rules.mjs`에서 적용한다. 판매 매출은 진열대 현금 더미에, 새 식사 매출은 해당 식탁 옆 대금에 쌓이고 플레이어가 회수한 뒤 소지금이 된다. 이전 저장의 여관 합산 대금은 호환 수금 더미로 유지한다. 방어 보상은 즉시 소지금으로 지급한다.
- 기본 이동 속도 수치를 월드 이동 속도로, Delay 계열 값을 생산 시간(초)으로 해석한다. 원작 런타임 단위가 완전히 복원됐다는 뜻은 아니다.
- 21레벨 마지막 성장의 짧은 순간이동, 전사→궁수→마법사 손님 순서, 구매 손님의 귀환 방어, 몬스터/외적 습격, 전투 보상은 이 웹게임을 위해 새로 만든 규칙이다.
- 습격 보상과 판매 환산은 높은 기존 성장 비용을 모바일 한 판에서 경험하도록 추가한 별도 규칙이다. 기존 비용 숫자 자체는 변경하지 않았다.
- 웹 고용은 기존 확률 4팩과 직원 80명의 개방 조건·등급을 사용해 후보를 뽑고 능력치를 실제 조수에게 적용한다. 원작의 고용/가챠 호출 흐름을 복원했다고 주장하지 않는다. 2026-10-30 재검토에서 `WorkerData_Stage1.workerMaxEmploy=5`를 확인해 조수 동시 상한을 이전 웹 설계의 3명에서 5명으로 맞췄다.
- 이동 마지막 강화의 순간이동은 거리 3.5, 대기 4초다. 일반 판매의 환산 배수 10·25·80·240·750·1500과 첫 습격 보상 3,000·8,000·24,000·72,000·216,000도 새 규칙이다. 기존 성장 비용과 속도/운반량은 그대로 유지한다.

## 이번 확장에서 실제 적용한 배열

시설은 1~3레벨의 **첫 form**에서 type 10을 생산/첫 상품 전달 준비/식사 초, type 30을 생산 재고 한도, type 20을 여관 매출 보너스 %로 해석한다. 대장간·연금 공방은 시간 `[3,2,1]`·적재량 `[4,10,14]`, 잡화점은 시간 `[2,1.5,0.9]`, 여관은 시간 `[5,4.7,3.7]`·보너스 `[0,0,5]%`를 사용한다. 상품 주문의 첫 전달을 카운터 시간만큼 준비하고 나머지는 0.22초마다 전달하며, 전부 전달한 뒤 수량×첫 전달 시 확정한 단가로 매출을 한 번 적립한다. 음식은 깨끗한 자리를 예약하고 첫 그릇부터 받으며 나머지를 0.22초마다 받는다. 식사 시간은 주문량과 별개로 여관 시간을 쓰고 식사 완료 대금은 수량만큼 계산한다. 선택 수치는 유지하며 웹에서의 단위·역할·전달 간격 적용은 해석이다. 다른 form은 보존하지만 선택·효과 전환 기능은 없다.

시설의 현재 레벨 `L`에서 다음 단계로 가는 비용은 기존 배열의 `costs[L]`다(0기반 배열). 따라서 대장간 120/1,990, 잡화점 100/1,750, 공방 330/2,090, 여관 370/1,200을 지불한다. `costs[0]`은 최초 개방 값으로 보존한다. 시작부터 열린 대장간/잡화점은 그 비용을 공제하지 않고 공방 230·여관 5만 개방 시 지불한다.

여관 비용 5에는 첫 식탁이 포함된다. 추가 식탁은 첫 지역 `Stage_1_Table_2`·`3`·`4`의 최초 `levelCost`인 **50·150·200**으로 차례로 개방한다. 이전처럼 여관 5를 지불하자마자 식탁 4개가 모두 열리지는 않는다. 각 식탁은 원문 `chairs`와 영상의 마주 앉은 손님을 참고해 **2좌석**을 두고, 자리마다 예약·착석·식사·더러운 식기·정리 상태를 따로 관리한다. 한쪽이 식사 중이어도 다른 쪽의 빈자리를 사용할 수 있다. 각 식탁의 별도 `Table.moneyArea`와 영상의 식탁 옆 현금 더미를 참고해 새 식사 매출은 같은 식탁의 대금에 합산한다. 깨끗한 빈자리가 없으면 배식 줄이 기다리고 청소·식탁 개방 후 다시 배식한다. 원문 객체·줄 번호·해시와 적용 한계는 [APK_SERVICE_REVIEW.md](APK_SERVICE_REVIEW.md)에 기록했다.

조수 공유 훈련 1~11레벨은 기존 선택 수치를 직원 기본 능력에 합성한다. 속도는 `직원 기본 속도 × worker.speeds[L-1] / worker.speeds[0]`, 운반량은 `직원 기본 운반량 + worker.capacities[L-1] - worker.capacities[0]`다. 각 훈련 비용은 기존 배열 `costs[L-1]`의 10개 값을 그대로 사용한다. 직원 `income`은 보존하지만 별도의 수익 배수로 적용하지 않는다.

일반 주문 후보의 원문 메서드와 초기화 값을 추가로 확인했다. 웹 일반 상품·음식 주문은 여관 미개방 또는 식탁 1개일 때 **1개**, 식탁 2~3개에서 **1~2개**, 식탁 4개에서 **2~3개**로 정하고 받은 수량을 순차 누적한다. 활성 식탁 수에 따른 원문의 `floor(식탁 수/4)` 증가와 기본 1~2개 범위를 판타지 품목에 적용한 것이다. 원작 첫 지역의 `GuideIndex ≤ 11` 튜토리얼 보정·다중 품목 배분·VIP·전화 주문의 모든 분기는 옮기지 않았다. 첫 지역 Counter의 `_maxItemValue=100`은 조사 기록으로 보존하고 웹 진열 상한 60을 유지한다. 원작 전체 주문·재고 규칙이 동일하다고 설명하지 않는다.

## 새 조작·지역·저장 규칙

정지 임계 0.4초, 물건 하나당 상하차·추가 주문 전달 간격 0.22초, 작업 원 반경 0.48·수금 원 반경 0.5·강화 원 반경 0.55와 정지한 상태의 수금는 사용자 요청을 반영한 신규 웹 규칙이다. 원작 영상의 정확한 상수를 복원한 것이 아니다. `action-zones.mjs`에서 판정·링·이동 버튼이 같은 중심과 반경을 가져오며, 각 시설/플레이어/조수 강화·고용·건설은 해당 원에 서야 지불한다. 0.25초 정지 진입 후 메뉴를 한 번 열고, 닫으면 원을 벗어나기 전까지 재열지 않는다. 머리 위 스택·공간에 남는 현금·카메라 구도 등 직접 확인한 원작 참고 근거와 미확정 관찰은 [RESEARCH.md](../RESEARCH.md)에 분리한다.

이동 중 인물끼리 겹치는 규칙은 유지한다. APK의 넓은 Trigger와 별도의 작은 NavMeshObstacle을 참고해 고정 시설의 몸체만 장애물로 삼는다. 빈 바닥에서는 직선 이동하고 시설에 막힐 때만 짧은 우회 경로를 쓰며, 주인공 조이스틱도 몸체 경계에서 막거나 미끄러진다. 손님을 장애물로 삼거나 줄을 피해 돌아가는 규칙은 추가하지 않는다. 웹의 시설 몸체·반경·경로 계산은 `shop-navigation.mjs`에서 새로 구현한 것으로 원작 NavMesh 데이터 복제가 아니다.

운반 표현은 `cargo-layout.mjs`의 공통 기준으로 머리 위 무기·물약·음식을 차례로 쌓고, 고객은 받은 상품·음식을 몸 앞에 든다. 포물선 출발·도착을 실제 재고와 운반 스택의 해당 층에 맞추고 비행 중인 물건을 도착 스택에 중복 표시하지 않는다. 새 층에는 상단 4층에 전달되는 340ms 감쇠 착지 반동을 준다. 실제 선반 재고와 비행 출발·도착점은 `stock-layout.mjs`의 표면별 층 좌표를 공유한다. 비행 시간 0.18초, 머리 위 기준 높이 1.4와 층 간격 무기 0.17·물약 0.31·음식 0.16은 웹 표현값이며 원작 모델 치수를 복원한 것이 아니다. 주문 말풍선의 `받은 수/전체 수`·전달 진행과 작업자 발밑의 상하차·정리 게이지는 서로 다른 상태를 표시한다. 원작 `ObjectGauge`의 모든 용도·표시 조건은 미확정이고, 새 웹 게이지를 원작의 공통 게이지로 설명하지 않는다.

일반 스테이지 10개의 기존 ID와 새 판타지 이름은 서로 다른 실제 웹 맵 배치에 연결했다. 지형·장식·시설/문 위치·동선은 새 제작물이며 원작 장면 복제가 아니다. 방어 승리 즉시 다음 지역으로 이전하고 10개 뒤에는 반복한다. 지도 목록 열람과 지역을 선택하는 자유 여행을 구분하며 후자는 구현하지 않았다.

스테이지의 오프라인 보상 필드와 이벤트 정의는 보존만 한다. 이벤트 야영지를 플레이 지역으로 열거나 원작 원격 설정을 적용하지 않는다. `runehaven:v1` 초기 저장은 새 필드가 없으면 시설/훈련 1레벨·현금 더미 0으로 보완하고 기존 재화·성장 기록을 유지한다.

식탁 확장과 2좌석 도입 후에도 v1을 유지한다. 이전 저장에 `dining.tableCount`가 없고 여관이 이미 열려 있으면 기존 식탁 4개를 보존하며, 새 상회는 1개부터 시작한다. 식탁별 `cash`가 없으면 0으로 보완하고 이전 여관 합산 현금은 지우지 않는다. 식탁 소유 수·개별 대금·좌석 상태는 현재 저장에 포함한다. 이전 1좌석 기록에는 새 두 번째 자리를 추가하고, 이전 사용 중·더러운 식탁 상태는 첫 자리의 정리 대상으로 옮긴다. 재접속 시 예약·식사 중 자리는 고객 객체 대신 정리할 자리로 복원한다.

미완료 주문의 전달분은 아직 결제되지 않은 재고로 취급한다. 손님 이탈·영업 중단 시 `returnedStock` 환입 대기분으로 돌리고, 저장 때도 미완료 손님의 전달분을 대기분에 포함한다. 진열·배식대 상한 때문에 즉시 돌려놓지 못한 수량은 보존했다가 빈 공간만큼 복구한다. 주문 도중 재접속해도 전달 재고가 사라지거나 미완료 주문의 매출·단골이 먼저 생기지 않도록 한 웹 저장 규칙이며, 원작의 환불·중단 처리를 확인한 결과는 아니다. 기존 저장에 이 필드가 없으면 품목별 0으로 보완한다.

## 라이선스와 한계

참고 게임의 규칙을 이해한 것과 게임 리소스를 사용하는 것은 구분한다. 현재 웹게임의 그래픽은 원본 APK에서 고른 실제 메시와 직접 작성한 도형·SVG로 구성한다. 원본 메시 11종은 Supercent 독점 자산으로 Kenney CC0와 구분하며, 원본별 SHA·면 수·변환 범위를 `assets/burger-source/manifest.json`과 `assets/burger-source/SOURCES.md`에 기록한다. 이미지·모델·아이콘·글꼴의 실제 출처와 라이선스는 `assets/SOURCES.md`에 기록한다.

참고 수치는 원작의 최신 버전·원격 설정·실험군·개인 저장 상태와 일치한다고 보장하지 않는다. 영상과 화면으로 확인한 내용의 범위는 `../RESEARCH.md`에 따로 기록한다. 게임 실행은 외부 조사 폴더에 의존하지 않는다.
